# 盘中断线与每日重启：选型结论

## 结论

目前不能把v40或v56判为适合无人值守盘中断线后自动恢复的已验收版本。v56可作为恢复工程的研究基础，但当前明确禁止live模式。已有收益排名不能解决恢复安全缺口。

## 代码证据与实测

| 项目 | 结果 | 含义 |
|---|---|---|
| v56专用信号测试 | 5/5通过 | 确认反转、库存规模规则，不是断线验收 |
| v40专用底仓恢复测试 | 3/3通过 | 正T信号补仓，不是未确认委托恢复 |
| 旧v49恢复套件对v56 | 29项，10失败、6错误、13通过 | 存在周期账本、runner键名和错误文本不兼容，不能将16项直接当成16个真实漏洞；也不能宣称套件通过 |
| v56在途标记重启 | 明确抛错阻断 | 需要对账，未实现直接自动续单 |
| v56无新旧检查点 | restore_checkpoint置checkpoint_active=True，未调用_broker_snapshot | 此恢复分支不能证明已核对券商委托；不等于已经证明会重复下单，仍需全流程测试 |
| v56真实库存或订单与保存快照不同 | 源码明确抛错 | 断线期间真实成交可能导致安全暂停，而非自动接续 |
| v56 live入口 | 直接抛出RESEARCH ONLY异常 | 当前不能作为可直接运行的实盘版本 |

直接恢复分支探针使用Mock，不连接券商，不发委托。实测输出：无检查点时activated=True、broker_snapshot_calls=0；inflight时抛出unresolved broker order错误。

v40源码未发现restore_checkpoint/checkpoint/inflight/order_uncertain相关实现。不能将“看到缺失底仓后买入”当作“恢复原委托与原T腿”。这属于本次源码检查范围内的结论，不是覆盖所有外部基础设施的证明。

## 对使用方式的具体回答

- 仅收盘后停止且当天订单全部确认、T腿闭合：风险较小，但仍要跨日保存并对账。
- 盘中断线但没有在途订单：v56有状态恢复结构，可继续做针对性验收，尚不证明全部场景安全。
- 盘中断线且有未确认/部分成交订单：目前应暂停交易并核对，不能要求重启后立即自动下单。
- 检查点丢失或损坏：不能根据仓位差猜测原T腿或自动补仓；完整启动链需补充针对性验收。

因此“每日做T哪个最优”的当前可证实答案是：没有通过该运行条件完整验收的赢家。研究开发优先v56；不建议因v40更容易重新启动就将其视为更安全或收益更优。

## 若继续实施恢复能力

需明确实现并测试：委托前持久化意图、券商成交唯一标识去重、断线成交补记、未确认订单锁定资金、部分成交与撤单竞态、检查点丢失时停止保护、跨日可卖股份核验、重启前后账本恒等。必须先用故障注入测试，不启用实盘来试错。

本轮只检查与测试，不修改策略、不解除实盘保护、不启动实盘。未新增收益回测；已有短期1分钟收益仅能支持v56作为研究候选，不能支持无人值守实盘推荐。
