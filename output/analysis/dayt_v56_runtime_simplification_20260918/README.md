# v56运行流程、机制与精简建议

> 分析对象：`Stragety/MiniQMT_Stragety/DayT/DayT_v56_nomom_ConfirmedReversalRiskBudget.py`  
> 分析日期：2026-09-18  
> 当前规模：约3,108行  
> 本报告只做结构和行为分析，不修改策略代码、不改变实盘参数。

## 一、结论摘要

v56目前不是一套单纯的“反T策略”，而是把以下五类职责集中在同一个文件中：

1. 反T信号计算和状态机；
2. 已被禁止下单的正T完整状态机；
3. 订单提交、成交确认、T+1、资金和持仓安全；
4. 双lane周期账本、checkpoint与手工订单对账；
5. 行情健康、连接监控、研究影子模型和大量解释性日志。

精简空间很大，但不能按“代码是否复杂”直接删除。建议分为三类：

- **可以直接从下一研究版本删除**：已硬关闭的FWD-T执行链、纯观察的`STRENGTH SHADOW`、仅输出日志的MA位置监控，以及相应状态、参数和日志。
- **适合移出主策略文件，但不应删除能力**：订单核验、checkpoint、手工交易对账、连接/报价健康、组合调度。这些是实盘安全模块，不是策略冗余。
- **必须先做消融回测再决定**：双lane、阶梯加仓、动态回落/反弹参考、quantile趋势阈值。这些会改变成交、收益和风险，不能在“精简代码”名义下直接移除。

如果只做行为保持型精简，预计主文件可以减少约500～800行；如果再把执行安全和持久化下沉为深层模块，主策略入口可缩到约800～1,200行，但总代码量不会等比例减少。

## 二、v56完整运行流程

```text
启动入口 main
  │
  ├─ 创建日志文件，记录源码路径/修改时间/SHA256
  ├─ live模式要求人工输入 yes
  ├─ 连接行情与交易账号，核对账号
  ├─ 启动watchdog并包装只读RPC超时监控
  ├─ 恢复v56 checkpoint
  │    ├─ 核对inflight/order_uncertain
  │    ├─ 核对券商持仓、订单及策略订单状态
  │    ├─ 恢复每只股票的L0/L1、周期账本和执行账本
  │    └─ 同步可唯一解释的手工交易
  │
  └─ 进入组合循环
       ├─ 每60秒刷新持仓、订单和手工成交
       ├─ 自动发现新持仓并创建L0/L1
       ├─ 每个lane完成交易日初始化
       ├─ 按到期时间串行推进各lane生成器
       ├─ 定期保存checkpoint
       └─ 异常或结果不确定时保留checkpoint并停止/暂停
```

单个lane在交易日内的流程：

```text
加载完整日线
  ↓
计算基础信号 + quantile趋势阈值 + ATR/成交量因子
  ↓
结合底仓、可卖数量、现金和其他周期预留计算容量
  ↓
盘中取得tick → 检查涨停保护/报价健康/停牌状态
  ↓
计算实际反T触发线
  ↓
IDLE
  ├─ 达到反T触发线 → SPIKING
  │                      ↓ 冲高延伸和回落均满足
  │                    卖出 → SOLD
  │                              ↓ 达到正常回落目标
  │                           DIPPING
  │                              ↓ 确认反弹
  │                           买回 → IDLE/DONE
  │
  └─ FWD-T路径仍会计算和展示，但开仓提交被硬禁止

未完成反T跨日
  ├─ 保留实际卖出腿、目标价和账本
  ├─ 每个交易日累计持有期
  └─ 达到最大持有期 → 强制按实际行情买回
```

## 四、可以删除的部分

### 4.1 FWD-T完整执行链

当前`LONG_RESEARCH_DISABLED=True`，`FWD-T buy`在订单提交入口被直接返回`SKIP`。但主文件仍保留：

- `do_long`、`long_lots`和现金容量计算；
- `buy_trigger`、floor、current-trail、max-trail；
- `STATE_BT_DIPPING/BOUGHT/SPIKING`；
- `_handle_bt_dipping/_handle_bt_bought/_handle_bt_spiking`；
- 正T阶梯买入、卖回和强制卖出；
- `DirectionalAdmission`分钟聚合和准入判断；
- FWD-T heartbeat、计划和阻断日志。

这部分属于“被硬关闭但仍持续运行计算”的历史包袱。若v56已经明确定位为反T策略，可以在新版本中完整删除，而不是继续保留开关。

删除前必须做一次checkpoint预检：所有现有v56状态中的`long_legs`、BT状态和正T周期必须为空。旧字段可以在读取时忽略或显式拒绝，不能静默丢弃未平腿。

**预计减少：250～400行。**

### 4.2 `STRENGTH SHADOW`

当前`INTRADAY_REFERENCE_MODE='shadow'`。该模块维护约十余个参数、历史分位、分钟采样、平滑强度、候选触发线和大量日志，但shadow候选不会替代实际执行触发线。

可删除：

- `IntradayStrength`、`StrengthConfig`、`lower_excursion_units`导入；
- `STRENGTH_*`参数；
- `_reset_strength_reference`至`_reference_log`中只服务strength的逻辑；
- `strength_armed`、候选状态和shadow日志；
- `shadow/active`双模式开关。

注意：不要把“动态回落/反弹参考”一起误删。当前shadow模式下，实际反T触发线仍可能来自`rebound_effective`，它和`STRENGTH SHADOW`不是同一个机制。

**预计减少：170～250行。**

### 4.3 MA5/MA20位置日志

`calculate_ma_position()`及`_maybe_report_ma()`当前主要输出观察日志，没有参与反T准入、触发或下单。若操作者不依赖该提示，可直接删除；如果仍希望诊断，可移到独立日志分析工具，而不是放在每个lane中重复计算。

**预计减少：30～50行。**

### 4.4 已关闭机制的兼容字段和旧命名

主文件仍使用`v52`作为checkpoint扩展键，并存在若干旧状态兼容字段。这些不能一次性直接删除，但可以在新版本使用独立checkpoint后清理：

- 新版本不自动导入旧v56 checkpoint；
- 启动时只做只读检查，确认没有未平腿；
- 新checkpoint采用当前版本命名；
- 删除仅用于旧版本迁移且已经完成历史使命的分支。

这属于状态格式迁移，不应和普通代码清理混在同一次提交中。

## 五、应当保留，但可以移出主文件

以下代码看起来很长，却承担真实资金安全职责，不建议删除：

### 5.1 订单执行安全

包括提交前checkpoint、订单号唯一性、同步等待成交、部分成交、未知提交结果、账户快照和实际成交价记录。建议形成深层模块`OrderExecutionGuard`，对策略只暴露类似：

```text
submit(intent) -> confirmed execution result / explicit uncertainty error
```

策略状态机不需要知道订单查询、回调竞争和状态码细节。

### 5.2 手工交易对账

当前`_reconcile_external_activity()`约143行，负责：

- 唯一手工T闭环；
- 永久底仓调整；
- 成交与持仓回报协调窗口；
- 单股票未完成订单隔离；
- 未跟踪订单的共享现金保护；
- 双lane周期归属核对。

建议形成深层模块`ManualTradeReconciler`，输入券商快照和策略账本，输出`SYNC_BASELINE/CLOSE_CYCLE/PAUSE_SYMBOL/BLOCK_ACCOUNT`等明确决策。不要把它简化为“发现数量不一致就覆盖baseline”。

### 5.3 checkpoint与恢复

持久化、原子写入、inflight、order_uncertain、券商快照一致性和跨日恢复必须保留。可以把版本迁移与运行时恢复拆开，减少`PortfolioRunner.restore_checkpoint()`中的分支数量。

### 5.4 连接、报价健康与watchdog

它们不产生收益，但用于解释“策略为什么没动”和识别RPC卡死。建议保留能力并集中到组合级别：同一股票的L0/L1无需分别探测完全相同的连接和报价健康。

## 六、不能直接删除，必须先做消融的机制

### 6.1 双lane

双lane不是单纯日志重复，它允许同一股票存在两个独立周期所有者，并与`MAX_OPEN_CYCLES=2`、总暴露上限、手工订单归属和checkpoint结构绑定。

改为单lane会改变：

- 同一触发时的卖出数量和分批方式；
- 第二个周期的入场时机；
- 阶梯追加和周期归属；
- 最大持有期回补数量；
- 收益、回撤和手续费。

建议单独建立“单lane v56”研究版本，用相同分钟数据比较收益、最大回撤、交易次数、未平腿和订单复杂度后再决定。

### 6.2 阶梯追加

`ladder_sell_target`允许反T卖出后价格继续上涨时追加卖出。它可能提高震荡收益，也会在持续上涨时扩大待买回库存。删除会改变风险和成交，必须单独消融。

建议比较：

- 阶梯开启；
- 阶梯关闭；
- 仅允许一个周期、无阶梯。

不要同时删除双lane和阶梯后只做一次比较，否则无法归因。

### 6.3 动态回落/反弹参考

该机制在当前shadow配置下仍可能改变实际反T触发线，因此不是纯日志。删除前应比较：

- 当前`rebound_effective`；
- 固定使用quantile基础触发线；
- 对成交次数、收益、最大回撤和上涨趋势中的未平腿进行分标的分析。

### 6.4 Quantile趋势阈值

这是当前首轮反T触发线的核心来源，并与`QUANTILE_UNITS_SCALE`研究结论绑定。不能因为实现复杂就改回固定ATR倍数；若要删除，应作为新策略机制研究，而不是代码整理。

## 七、建议的目标结构

当前继承关系为：

```text
ExecutionRunner（约1680行）
  └─ StrategyRunner（约328行）

ExecutionPortfolio（约280行）
  └─ PortfolioRunner（约386行）
```

基础实现和v56覆盖都在同一文件，调用者必须理解大量隐式状态和覆盖关系，属于界面较大的浅层结构。建议调整为：

```text
v56策略入口
  ├─ RevTPolicy
  │    输入：完整日线、tick、当前周期
  │    输出：WAIT / SELL / BUYBACK意图及原因
  │
  ├─ CycleLedger
  │    管理：lane、腿、周期、手续费未知状态、最大持有期
  │
  ├─ OrderExecutionGuard
  │    管理：提交、订单号、成交、部分成交、未知结果
  │
  ├─ ManualTradeReconciler
  │    管理：手工T、底仓调整、暂停范围
  │
  └─ PortfolioRuntime
       管理：连接、调度、行情健康、checkpoint、watchdog
```

每个深层模块都应只有一个小界面；不要把现有3108行机械拆成多个同样互相读写`st`字典的小文件，否则只是移动代码，并没有降低复杂度。

## 八、推荐实施顺序

### 第一阶段：行为保持型精简

1. 新建独立版本，不直接在当前实盘v56上大删。
2. 删除`STRENGTH SHADOW`及其参数、状态和日志。
3. 删除MA5/MA20纯观察日志。
4. 删除FWD-T完整链路，但先验证所有checkpoint不存在正T未平腿。
5. 保持REV-T信号、双lane、阶梯、quantile、动态反弹、最大持有期和所有执行安全逻辑不变。
6. 跑完整DayT测试、冻结黄金回放，并逐笔比较REV-T订单与当前v56完全一致。

这一阶段的验收标准不是“收益接近”，而是REV-T触发、委托、成交和收益逐笔一致。

### 第二阶段：结构下沉

1. 提取`OrderExecutionGuard`；
2. 提取`ManualTradeReconciler`；
3. 提取`CycleLedger`；
4. 将报价健康和连接探测提升到组合级；
5. 用模块界面测试替代对大量私有方法的直接测试。

这一阶段只移动职责，不改变策略行为。

### 第三阶段：机制消融

按一次只改变一个变量的原则依次研究：

1. 阶梯开启/关闭；
2. 双lane/单lane；
3. 动态回落参考/固定quantile触发；
4. 最后才考虑进一步简化quantile或再入场。

每项都使用相同的一分钟数据、手续费、T+1、初始底仓和连续账户口径，输出收益、超额收益、最大回撤、未闭合腿、持有天数和手续费。

## 九、最终保留的最小v56机制建议

若目标是“尽可能简单但仍适合实盘的反T策略”，建议最小集合为：

- 完整日线数据校验；
- quantile/ATR反T触发线；
- 冲高延伸+回落确认；
- 正常回落目标+反弹确认买回；
- 最大持有期买回；
- 单标的总暴露上限；
- 涨停、T+1、现金和整手限制；
- 订单、成交和未知结果核验；
- 周期账本、checkpoint、跨日恢复；
- 手工交易对账；
- 连接、报价健康和watchdog。

优先移除：

- FWD-T及DirectionalAdmission；
- `STRENGTH SHADOW`；
- MA位置观察；
- 对已删除机制的旧状态和重复日志。

待回测后再决定：

- 双lane；
- 阶梯追加；
- 动态回落/反弹参考。

这个顺序能先删除不影响实际下单的复杂度，再通过消融决定哪些“会影响收益的复杂度”真正值得保留。
