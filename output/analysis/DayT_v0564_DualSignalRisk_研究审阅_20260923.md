## 策略结构

### 外层：日线双信号风控

外层每天根据日线计算两个参考信号：

```text
exit_signal  = close < running_peak - 3 × ATR
entry_signal = close > MA20
```

其中：

- `exit_signal=True` 表示市场风险较高，倾向清仓；
- `entry_signal=True` 表示价格位于 MA20 上方，倾向持仓或回场；
- `RISK_RESOLVE_MODE` 决定两个信号冲突时的最终状态；
- 每个交易日原则上只执行一次清仓或回场动作。

当前默认模式为 `EXIT_PRIORITY`。

### 内层：日内反 T / 正 T

反 T 流程：

```text
IDLE
  → 价格突破卖出触发线
SPIKING
  → 至少观察 2 个 tick/bar
  → 相对触发线延伸至少 0.15%
  → 相对峰值回落至少 0.20%
SELL
  → 以对手价卖出
SOLD
  → 相对实际卖出价下跌 ATR% × 0.15
DIPPING
  → 从低点反弹至少 0.10%
BUYBACK
  → 以 ask1/fallback 限价买回
DONE
```

正 T 流程：

```text
价格下跌到动态买入线
  → 反弹确认后买入
  → 上涨约 1.20%
  → 从峰值回落约 0.10%
  → 卖回
```

仓位规则：

- 单次目标金额为 40,000 元；
- 最多使用约 40% 可配对底仓；
- A 股买入按整手处理；
- 当前日志显示持仓 100 股、现金约 6,700 元，因此实际只能做一手反 T；
- 正 T 因现金不足及 T+1 配对容量不足而被阻止。

## 核心缺陷：双信号裁决没有解决翻仓

当前裁决逻辑可概括为：

```python
if mode == 'EXIT_PRIORITY':
    if risk_on:
        risk_on = not exit_signal
    else:
        risk_on = entry_signal

elif mode == 'ENTRY_PRIORITY':
    if not risk_on:
        risk_on = entry_signal
    else:
        risk_on = not exit_signal
```

两个分支实际完全相同，只是条件书写顺序不同。

直接运行当前函数后得到：

- 连续 15 天 `exit=True, entry=True`；
- `EXIT_PRIORITY` 输出 `OFF、ON、OFF、ON……`；
- `ENTRY_PRIORITY` 输出完全相同的结果；
- `HOLD` 在冲突时能保持前值，但在 `exit=False, entry=False` 时会错误切换为 `OFF`。

日志也呈现相同现象：

- 9 月 21 日：`exit=True + entry=True + EXIT_PRIORITY`，结果为 `RISK-ON`；
- 9 月 22 日：同样的双信号冲突，结果变为 `RISK-OFF`；
- 9 月 21 日计划日志说“出场优先，今日清仓”，实际却保持 `RISK-ON` 并执行了反 T。

因此，计划描述、裁决结果和真实动作互相矛盾。

### 建议采用的裁决真值表

| exit | entry | 基础行为 |
|---:|---:|---|
| False | False | 保持前值 |
| False | True | `risk_on=True` |
| True | False | `risk_on=False` |
| True | True | 交给冲突模式裁决 |

冲突时：

- `EXIT_PRIORITY`：切换为 `OFF`；
- `ENTRY_PRIORITY`：切换为 `ON`；
- `HOLD`：保持前值。

### 更深层的策略问题

日志中的关键位置为：

```text
MA20 = 428.16
stop = 501.56
close = 458.99
```

双稳区宽约 73 元，相当于现价约 16%。这不是偶发边界，而是很宽的常态区间。

修正软件错误后：

- EXIT 优先可能在整个冲突区长期空仓；
- ENTRY 优先可能在整个冲突区长期满仓，相当于弱化外层风控；
- HOLD 的结果高度依赖进入冲突区前的状态；
- 若没有可靠持久化，HOLD 的“前值”在重启后并不可信。

所以第三规则实际已经成为策略的主要方向判断。三种模式必须通过统一口径回测比较，不能凭模式名称直接决定默认值。

## P0：实盘安全问题

### 尾盘强平读取不存在的字段

尾盘处理读取：

```python
shares = int(self.st.get('sell_shares', 0))
```

但策略没有任何位置写入 `sell_shares`。真实未回补数量保存在 `short_legs` 中，因此尾盘得到的数量通常永远为 0。

此外，尾盘只处理 `STATE_SOLD`，不处理已经到达回补目标并正在等待反弹的 `STATE_DIPPING`。如果尾盘处于 `DIPPING`，也不会执行回补。

这与策略“No carry”和“尾盘强平未闭合腿”的声明直接冲突。

### 没有 checkpoint，重启会丢失开放腿

`PortfolioRunner.save_checkpoint()` 直接返回 `None`。重启后会丢失：

- `short_legs` 和 `long_legs`；
- 当日成交次数；
- 已处理订单号；
- 累计收益；
- 风控清仓数量；
- 前一日风险状态。

如果策略在反 T 卖出后、买回前退出，重新启动后无法可靠判断账户减少的持仓来自策略反 T、人工交易还是风控清仓。

日志显示 9 月 21 日存在多次重启。本次重启都发生在没有开放腿或周期已经闭合时，因此没有暴露事故，但不能据此认为重启安全。

### 固定 800 股回场可能扩大持仓

策略固定设置：

```python
BASE_TARGET_SHARES = 800
```

当前实际持仓只有 100 股。风险清仓时没有持久保存“实际卖出多少股”，风险恢复时却计划买入 800 股，仅依靠现金余额进行钳制。

当前资金只能买回约 100 股，因此暂时不会放大仓位；如果以后账户现金充足，则可能从原来的 100 股恢复为 800 股，产生非预期风险敞口。

正确做法是记录风控清仓的实际成交数量，并让回场数量严格不超过该数量。

### 风控动作只尝试一次

策略在实际执行风控订单前就把 `risk_switch_done` 标记为当日完成。

若出现以下情况，当天也不会重新尝试：

- 可卖数量暂时为 0；
- 废单或拒单；
- 部分成交；
- 现金或持仓回报尚未更新；
- 下单入口返回 `SKIP`。

最新日志显示：

```text
RISK-OFF 空仓
ACCOUNT 100 sh (sellable 0)
```

这说明 `RISK-OFF` 只是目标风险状态，账户实际上仍持有 100 股。当前日志把目标状态描述成“空仓”，容易导致人工误判。

建议拆分：

- `desired_risk_on`：目标风险状态；
- `actual_position_state`：真实仓位状态；
- `risk_transition_status`：未执行、委托中、部分完成、已完成、失败待处理。

### 风控数据错误时 fail-open

风险日线不可用时，当前代码设置 `risk_on=True`。这会在风险层失效时放开内层交易。

更稳妥的策略是：

- 不因为数据异常自动清仓；
- 但应禁止新开反 T/正 T 腿；
- 允许已有开放腿执行必要的风险收尾；
- 数据恢复并通过健康检查后再恢复新交易。

## 信号时间问题

### 盘后信号基准被旧开盘价覆盖

代码首先规定盘前和盘后使用最新完整收盘价作为信号基准，随后只要 tick 中存在 `open`，又立即用该开盘价重算触发线。

最新日志显示：

```text
收盘价：456.60
tick 中开盘价：469.00
触发价：465.78 → 478.43
```

这说明盘后计划最终仍使用当天旧开盘价，而不是代码声明的最新完整收盘价。

下一交易日真实开盘价到达后可能再次修正，但当前代码把 09:25—09:30 归入上午交易时段，存在使用旧开盘价提交订单的窗口。

建议：

1. 09:30 前仅生成预览，不提交新开腿或风控订单；
2. 获取当日有效开盘价后重新计算执行触发线；
3. 盘后预览不得修改次日执行锚点；
4. 日志分别展示 `preview_anchor` 和 `execution_anchor`。

## 状态与日志可观测性问题

### 跨日后不再打印收盘摘要

`_post_market_printed` 在第一次盘后摘要后被设置为 True，但每日初始化没有重置该字段。

完整日志在第二个交易日收盘后只有 `[POST]` 心跳，没有新的 `[CLOSE]`、`[FLIP]` 和 `[ZONE]` 摘要，符合这一缺陷的表现。

### “累计翻仓”并不累计

每日初始化会把 `_risk_flip_count` 重置为 0。因此日志中的“累计翻仓”不能跨交易日，更不能跨进程重启。

### 日志噪声过大

完整日志共约 776 行，其中：

| 类型 | 数量 |
|---|---:|
| `HB` | 241 |
| `WAIT` | 113 |
| `POST` | 74 |
| `LUNCH` | 18 |
| `LATE` | 7 |
| 成交 | 2 |

核心事件被大量心跳信息淹没。建议：

- 正常心跳继续写文件，但降低到 5—30 分钟一次；
- 状态变化、订单、成交、异常仍立即输出；
- 相同内容使用状态去重；
- 每日生成一段紧凑汇总。

### 毛收益与净收益混淆

`ExecutionBook` 明确只记录 gross，不估算费用。日志虽使用 `gross` 字样，但停止摘要 `gross~Y380` 容易被误读为实际盈利。

建议同时输出：

- 成交价差毛收益；
- 券商已知费用；
- 估算或账户差额净收益；
- 对费用未知部分明确标记 `UNKNOWN`，不得默认计为零。

## 其他研究问题

### 当前 ATR 实际是平均日内振幅

代码用近 14 日 `high-low` 的均值作为 ATR，没有纳入：

```text
abs(high - previous_close)
abs(low - previous_close)
```

因此它更接近 ADR，而不是标准 true range ATR。对跳空较多的高波动股票，这可能明显改变风险止损线和买回距离。

建议把“保持当前 ADR 算法”和“改用标准 ATR”作为独立消融实验，不能与裁决器修复混在同一轮结果中。

### 280 日重放仍有状态边界

HOLD 需要知道冲突区之前的风险状态。当前只重放最多 280 根日线，并从 `risk_on=True` 开始。

如果冲突或无信号状态持续到覆盖整个窗口，真实前值已经丢失；随着窗口滚动，结果还可能变化。HOLD 应依赖持久化状态，或使用明确且经过验证的 bootstrap 规则。

### 缺少专项测试和研究记录

当前测试目录没有引用 v0564 的专项测试。现有 [`StrategicResearchDirectionsAndEffectivenessRecords.md`](../Stragety/MiniQMT_Stragety/DayT/StrategicResearchDirectionsAndEffectivenessRecords.md) 也没有 v0563/v0564 记录。

按照仓库研究约定，v0564 至少应登记为“待验证”，并记录：

- 研究假设；
- 相对 v0563 的唯一主要变化；
- 当前已知缺陷；
- 日志与测试证据；
- 统一回测口径；
- 不开放实盘或恢复实盘的门禁条件。

## 最终建议

短期建议是停止 v0564 的真实下单，只做信号或影子运行，先修复裁决器、尾盘回补和重启恢复。

策略机制上，不建议把修正后的 `EXIT_PRIORITY` 直接当作最终方案。更合理的研究方向是持久化滞回状态机：

- 明确一个出场阈值；
- 明确一个更严格的回场阈值；
- 两个阈值之间保持已持久化的前值；
- 重启时通过 checkpoint、券商订单和实际持仓恢复状态；
- 无法唯一恢复时锁定交易并要求人工对账。

这样双稳区才会成为稳定缓冲区，而不是由历史冲突天数奇偶、进程重启或默认初始值决定仓位。

按照仓库版本约定：裁决真值表、尾盘字段、日志和恢复安全属于缺陷修复，可以继续修正 v0564；如果进一步改变出场/回场阈值或引入新的滞回机制，则应新建策略版本，并同步更新研究记录。
